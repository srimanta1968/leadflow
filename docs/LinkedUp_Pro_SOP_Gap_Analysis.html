Lynked Up Pro — Prelaunch License Sales SOP v3.0
vs. ProjexCRM Implementation

A requirement-by-requirement mapping of the 50-page “ProjectLight CRM | Expanded Playbook Edition” SOP against what actually exists in the projex_crm codebase — with file-level evidence, verdicts, and a prioritized remediation roadmap.

SOP source: Lynked_Up_Pro_Prelaunch_License_Sales_Playbook_…_v3.0.pdf Analysis date: 14 Jul 2026 Codebase: C:\projex_crm (branch main) Method: 5 parallel code-exploration passes across all P0 domains

Overall verdict: MATERIAL GAP — NOT LAUNCH-READY AGAINST THIS SOP

ProjexCRM is a strong, mature outbound AI-prospecting & email-sequence engine. The SOP, however, specifies an inbound “speed-to-lead” human sales operation — 30-minute SLA, multi-rep routing with backup coverage, mandatory NEXT-action enforcement, a live leadership queue, multi-channel (SMS/phone) contact, and a closed-won→onboarding commerce handoff. That operational backbone is largely absent. Of the SOP’s twelve P0 “launch-blocker” capabilities, none are fully met, roughly seven are partial, and four to five are missing. The email/sequence/suppression machinery is genuinely excellent and reusable; the inbound-ops, routing, SLA, telephony, and commerce layers must be built.

Data-model objects solid
The single most important finding — an orientation mismatch. The core data model is prospect-centric and single-operator: a prospects table flows new → validated → contacted → engaged → responded → promoted, and “leads” are a promoted subset (promoted_to_lead_id). There is no rep-capacity model, no availability/PTO, no round-robin, and no automated routing. The SOP assumes a staffed team queue where every inbound signal is routed, owned, backed-up, and SLA-timed. Closing these gaps is a feature-build, not a configuration exercise.

4 · Deep-dive — Lead Intake, Canonical Identity & Routing

4.1 Universal lead intake

PARTIAL
Channels that work todayOK

Appointment booking form (public-capture.routes.ts:518), event registration (public-events.routes.ts:169), Chrome-extension LinkedIn scrape (extension-capture.service.ts:114), manual API create (leads.routes.ts:279), external-app conversion + funnel-event webhook (public-lead-convert.routes.ts:38, public-track-event.routes.ts:75).

Channels the SOP requires but are absentMISSING

Inbound phone calls (no call ingestion), live chat, referral intake, checkout-started / purchase-completed e-commerce events, and generic inbound social DM. Raw-payload retention is weak — there is no generic store for inbound form/webhook submissions.

Watch-out: despite its name, channel-ingestion.service.ts ingests LinkedIn/email performance metrics, not leads.

4.2 Canonical identity & dedupe

PARTIAL
Matching keys implementedOK

Priority order LinkedIn URL → lowercased email → name+company (global-contact.service.ts:322-392); tenant-unique indexes on (org|user, email) and (…, linkedin_url).

Keys the SOP requires but are missingMISSING

E.164 phone (phone is stored but never a match key and never normalized), transaction/order ID, and domain-canonical company identity. Merge lineage is not durably preserved — lead-dedup.mergeLeads hard-deletes secondary rows (:302) and prospect merged_from stores source labels, not record IDs.

4.3 Ownership, backup & routing

PARTIAL / MISSING
Single-assignee delegation existsPARTIAL

owner_id / member_id / assigned_by / assigned_at with a PATCH /:id/assignee endpoint gated by team membership, plus an owner↔assignee message thread (leads.routes.ts:1085, :786).

Backup coverage & auto-fallbackMISSING

No backup rep, no manager on the lead, no accept/decline + accepted_at, no capacity/PTO/out-of-office, and no automatic fallback — reassignment is entirely manual.

No routing engine, no round-robin/pool distribution, no P0/P1/P2/P3 tiers. Lead priority is a free string (low/medium/high). lead-prioritization.service.ts ranks leads by buying-intent score — it does not route them to reps.

Webhook idempotencyPARTIAL

Only Stripe dedupes replays — via an in-memory Set of the last 1000 event IDs (non-durable). Inbound lead/appointment/conversion webhooks have no idempotency keys.

5 · Deep-dive — SLA Clock, Escalation & NEXT-Action

This is the SOP’s spine — and it is essentially unbuilt. The “30-minute human response,” the T+15/25/30/45 escalation ladder, and “no blank NEXT” are the SOP’s three non-negotiables. None have a runtime implementation.
30-minute speed-to-lead SLA clock (America/Chicago, business hours)MISSING

No time-to-first-contact timer, no responded_at/breach fields, no America/Chicago reference anywhere. Business-hours config exists (business-context.service.ts:23, default 09:00–17:00 / America/New_York) but feeds only calendar availability & email formatting.

Tiered escalation ladder (rep→backup→manager→director)MISSING

notification.service.ts is a flat DB store with no timing/escalation. Event & booking notifications only email the registrant/salesperson. Nothing time-based reassigns to a backup or pages a manager/director.

Mandatory NEXT-action enforcement (blocks save/advance)MISSING

No NEXT-action column or object; lead update/stage endpoints perform no required-field validation. Records can be saved/advanced with a blank next step.

Task queue (owner / priority / completion / overdue)PARTIAL

Closest is followup_schedules, which auto-fires due items (sends a message) rather than surfacing a human to-do. No per-task owner, no priority, no human completion, no overdue flag.

After-hours queue-for-morning + 8:30/4:45 digestsMISSING

No “queue until next business morning” path and no twice-daily operating-rhythm digest. Scheduled workers exist (sequence tick, inbox sync, bounce sync, weekly feedback) but none implement the SOP cadence.

6 · Deep-dive — Communications, Sequences & Consent

This is the codebase’s strongest domain. The email + sequence + suppression stack is production-grade and directly reusable — the gaps are the additional channels (SMS/phone) and a few event-branch behaviors.
Automated send channelsPARTIAL

Email fully automated (Nodemailer + SendGrid/Mailgun/Postmark, email-sender.service.ts, email-outreach.service.ts). LinkedIn DM is manual-assist — the server marks steps ready and a Chrome extension sends after human approval (linkedin-social-outreach.service.ts:824). SMS / phone / voicemail: none — they appear only as channel-scoring outputs, never as a send path.

Reply detectionIMPLEMENTED

Inbound email matched by In-Reply-To/References then auto-pauses sequences (inbox-sync.service.ts, email-outreach.service.ts:1763); LinkedIn DM replies trigger sentiment + engagement boost + stage advance.

Sequence orchestrationPARTIAL

Event-driven 60s-tick engine: pause-on-reply ✓, stop-on-opt-out ✓, event triggers (registration/attendance/no-show/booking) ✓, send idempotency ✓. Replace-CTA-on-booking only adds a parallel reminder sequence (doesn’t swap the “book a call” CTA or halt the in-flight chase). Stop-on-payment not implemented (payment = SaaS billing only).

Consent & suppressionPARTIAL

Token opt-out/DNC with reason codes, reason-tagged email_suppression_list, provider bounce auto-suppression, per-lead frequency caps (24h cooldown / 5 max) — all solid. Gaps: suppression is per-tenant (not cross-org global DNC); quiet hours use the sender/business timezone (not recipient-local); no SMS STOP/HELP; explicit opt-in consent evidence is thin.

Unified activity timelinePARTIAL

Per-lead JSONB activity_log is email/appointment-centric (no SMS/call/DM/note types) and capped at 100 entries; LinkedIn DMs, communication_logs, and deal_activities live in separate stores — not one chronological stream.

7 · Deep-dive — Calendar, No-Show, Payment & Onboarding

Calendar / booking enginePARTIAL

Real availability with IANA-tz math, double-book prevention, event IDs, ICS invites, public booking page. But two-way Google/Microsoft sync is simulated (calendar-integration.service.ts:230 — “we simulate by creating sync log entries”; Google OAuth requests only openid email profile, no calendar scope). No round-robin/pooled hosts; no meeting types — all bookings default to fixed 30-min slots.

Reminders / reschedule / cancelPARTIAL

Booking confirmation email + ICS to both parties works. But no timed 24h/2h/15m pre-meeting reminders, and the confirmation says “contact us to reschedule” — no self-service reschedule/cancel link.

No-show handlingPARTIAL

For 1:1 sales meetings: missing — the cleanup worker marks every past appointment completed regardless of attendance. An on_no_show branch exists only for webinar/event registrations (requires attendance to be marked manually).

Payment / checkout for closed-wonMISSING

Stripe = the CRM’s own subscription + credit-pack billing. There is no “sell the prospect a license” checkout, no started/pending/failed/success state tied to a deal, no verify-before-Closed-Won gate, and no license/transaction ID issued to a prospect.

Closed-Won → onboarding handoffPARTIAL

A “Closed Won” stage exists and stage-entry can fire a generic configured sequence. But nothing suppresses in-flight presale sequences on won, no customer/license record is created, and no onboarding handoff task/workflow with a named CS owner is generated. OnboardingPage.tsx is CRM-user signup, not customer onboarding.

Payment webhook idempotencyPARTIAL

Signature verification via stripe.webhooks.constructEvent ✓. Idempotency is in-memory only (last-1000 Set) — a duplicate event after a restart could reprocess subscription state.

8 · Deep-dive — Dashboards, RBAC & Audit

Leadership operational dashboardMISSING

Existing dashboards are marketing/engagement-oriented (open/response/click/booking rates; a rep recommendation queue). None of the SOP leadership signals exist — leads-waiting, oldest-wait, SLA at-risk/breached, unowned records, missing-NEXT, failed-messages, purchases-awaiting-onboarding, stale-opportunities.

RBAC rolesPARTIAL

Two disjoint systems — app RBAC admin/agent/viewer (rbac.service.ts:24) and team membership owner/admin/member/viewer. Neither models the SOP’s Rep / Manager / RevOps / Leadership hierarchy, and gating is coarse.

Immutable audit / versioning / retentionPARTIAL

Insert-only access_logs exists but covers auth events only. No template version history, no configurable retention, no incident-evidence store. error-logger.service.ts is an in-memory ring buffer (lost on restart) — not durable audit.

Exception / incident objectMISSING

No incident object with type / affected-records / root-cause / owner / recovery. Nearest artifacts are crm_integration_errors / crm_sync_conflicts, which don’t model ownership or recovery.

9 · Strengths — reusable assets to build on

  • Production-grade email engine — multi-provider send, batch, and a lock-safe send_queue (FOR UPDATE SKIP LOCKED, per-user/global rate limits, source_ref_id dedup). Directly reusable for the SOP’s email sequences.
  • Deep consent/suppression & deliverability — token opt-out with reason codes, reason-tagged suppression list, provider bounce classification + auto-suppression, per-account bounce-rate auto-pause, per-lead frequency caps. This satisfies much of SOP §21 “Compliance/QA” for email.
  • Event-driven sequence orchestrator — 60s tick with condition eval, send-window gating, credit gating, pause-on-reply, stop-on-opt-out, and event triggers. The right foundation to add replace-CTA-on-booking and stop-on-payment.
  • Reply intelligence — IMAP inbox sync with header-based thread matching + sentiment; a strong base for the SOP’s “any reply pauses automation & creates an urgent owner task.”
  • Booking/availability core — real timezone math, double-book prevention, ICS invites, public booking page — a solid base once real Google/MS sync and reminders are added.
  • Configurable funnel + deals + activities — the object graph to hang the SOP stages/NEXT-actions on already exists; it needs enrichment and guardrails, not a rebuild.
  • Multi-tenant, sharded, auditable auth — RBAC scaffolding, immutable auth log, MFA, encryption service — extendable to the SOP role model.

11 · Prioritized Remediation Roadmap

Ordered by SOP criticality × build effort. Phase 1 items are the SOP’s non-negotiables and hard launch blockers.

Phase 1 — Inbound sales-ops backbone (the SOP’s non-negotiables)

  • 1SLA clock & escalation engine. Add first-response tracking (first_attempt_at, sla_due_at, breach_at) on the America/Chicago business clock, plus a T+15/25/30/45 escalation ladder with backup + manager + director alerts. Blocker #2/§04.
  • 2NEXT-action object + save-gate. First-class task (type, owner, due-time, purpose, intended outcome); block save/stage-advance on non-terminal records when NEXT is missing (SOP §06/§28 save-gate).
  • 3Ownership + backup + routing. Add backup rep, manager, accept/decline (accepted_at), capacity/PTO; build the eligibility→priority→specialty→availability→assignment→fallback router with P0–P3 tiers and round-robin.
  • 4Leadership operating dashboard. Surface leads-waiting, oldest-wait, SLA at-risk/breached, unowned, missing-NEXT, failed-messages, purchases-awaiting-onboarding, stale-opportunities.

Phase 2 — Channels, commerce & onboarding

  • 5SMS channel (Twilio) with STOP/HELP, quiet hours in recipient-local time, delivery receipts, and the SMS template library from SOP §18/§36.
  • 6Phone/dialer + voicemail logging — at minimum a tracked-call disposition + voicemail-flag so a “valid human attempt” (SOP §04) can be recorded; power-dialer is P1.
  • 7Closed-won commerce & onboarding. Prospect license checkout, verify-payment-before-won gate, customer/license record, presale-sequence suppression on won, and an onboarding handoff object with a named CS owner + kickoff scheduling (SOP §19).
  • 8Real calendar two-way sync (Google/MS Graph with calendar scopes), meeting types (15/30/60), timed 24h/2h/15m reminders, self-serve reschedule/cancel, and 1:1 no-show detection + rebook.

Phase 3 — Intake breadth, compliance & resilience

  • 9Intake breadth + raw-payload store + webhook idempotency keys across all inbound connectors (forms, chat, referral, checkout, purchase, inbound call, social DM).
  • 10Identity hardening — E.164 phone normalization + phone/transaction-ID match keys, domain-canonical accounts, and a durable merge-history table (stop hard-deleting merged rows).
  • 11Offer-truth & feature-status matrix — versioned Offer Data Sheet, deal offer_version, LIVE/BETA/ROADMAP labels enforced in demo/commercial stages.
  • 12Governance — SOP role model (Rep/Manager/RevOps/Leadership), incident/exception object with recovery workflow, durable audit + template version history + retention controls, and the 8:30/4:45 digests.
