InboundCRM — Build Strategy Analysis

What is the fastest, safest way to deliver the Lynked Up Pro inbound-sales SOP? This originally compared four build strategies and recommended a ProjexCRM-lift hybrid. It has since been revised (15 Jul 2026): the decision pivoted to build the missing capabilities as reusable ProjexCloud SDKs rather than lift/copy ProjexCRM — and an authoritative SOP re-validation reduced the ProjexCRM copy-list to zero. Decision update (15 Jul 2026) — supersedes the original recommendation. The team chose not to lift/copy ProjexCRM code into the app. Instead, every capability the SOP needs is being delivered as a reusable ProjexCloud SDK (new or extended), so it benefits every future customer — not just InboundCRM. Two verification passes drove this: (1) an authoritative re-read of the SOP PDF found none of the 7 proposed ProjexCRM copies is a P0 requirement → copy nothing; (2) a code-level audit confirmed the reusable mechanisms already exist in the SDK platform, needing only thin new domain SDKs + one bug fix. The outreach engine (the old “lift” half) is now built as the P14 SDKs sdk-sequence / sdk-scheduling / sdk-deliverability; the remaining SOP objects as the P15 SDKs sdk-offer-catalog / sdk-handoff / sdk-incident / connector-twilio-voice.

Revised recommendation: SDK-ONLY — build the gaps as reusable SDKs, copy nothing

Deliver InboundCRM as an SDK-only app on the ProjexCloud platform. The reason Strategy B was originally dinged — “it forces you to rebuild the email/sequence/calendar layer the SDKs lack” — is resolved by building those layers as first-class SDKs (P14), so the rebuild happens once and is reusable forever, instead of lifting app-specific ProjexCRM code that helps only this customer and drags coupling. The SOP re-validation confirms the copy-list is empty: every ProjexCRM capability either maps to an existing/new SDK or is dropped (outbound prospecting, LinkedIn, AI-agent mesh). InboundCRM then consumes the SDKs and adds only its customer-specific config/content.

Why not A (lift) after all? Lifted code is app-specific, non-reusable, and imports coupling (billing gate, prospecting refs, agent-mesh registration) you must then sever. Worse, the SOP doesn’t actually require the lifted files. Building the outreach engine as SDKs is marginally slower once, but reusable across every future vertical and coupling-free.

6 · Phased delivery plan (SDK-only)

Phase 1 builds the reusable SDKs (P14 + P15, already tracked in ProjexLight); Phase 2 assembles the InboundCRM app on top. Sequenced so the SOP’s non-negotiables land first.

1

Build the outreach SDKs (P14) · planned + tracked

Ship sdk-sequence (cadence, step-executor, send-window, reactive stops, guardrails), sdk-scheduling (availability, booking, ICS, reminders, no-show, 2-way sync), sdk-deliverability (suppression, bounce webhooks, IMAP reply-sync), plus sdk-crm/sdk-notification/sdk-assignment extensions. Dependency root: sdk-sequence schema (TK-3612).

2

Build the SOP-gap SDKs (P15) · planned + tracked

sdk-offer-catalog (launch-blocker #1), sdk-handoff, sdk-incident, connector-twilio-voice, plus the sdk-crm call-activity + sdk-connectors DLQ extensions. All thin domain layers on existing patterns.

3

Scaffold the InboundCRM app (SDK-only)

AI-planner /build on the InboundCRM intent → projex init inbound-crm → projex install each SDK → compose an api-gateway-style backend (register each SDK’s routes + one runMigrations([...])) → Next.js UI on @projexlight/design-system. Single DB (no db.config.json).

4

Wire the SOP’s 12 P0 capabilities + app-build items

Lead intake, identity/dedupe, SLA clock + escalation, routing + backup, NEXT-action gate, two-way comms, consent/suppression, sequence, calendar, payment/onboarding, dashboards, security/audit. Build the app-only pieces: leadership dashboard, next-best-action, onboarding saga content, and customer config (stage values, disposition codes, roles).

5

Governance, go-live packet & re-audit

Offer-truth version-stamping in the CRM, operating-rhythm digests, the SOP go-live test packet, and a code-level re-run of the ProjexCRM→ProjexCloud coverage audit to confirm no covered capability regressed to a gap.

7 · Risks & mitigations

RiskMitigation
Building the outreach SDKs is more up-front work than liftingThe logic is proven in ProjexCRM (re-home, don’t re-invent); the cost is paid once and amortised across every future customer. Tracked as 47 tasks with acceptance criteria + 87 BDD scenarios before coding.
Thin SDK test coverage (many SDKs ship 0 test files)Every P14/P15 feature already carries BDD acceptance scenarios; add integration tests at the SOP-critical seams (sequence executor, suppression, save-gate, handoff accept/reject, DLQ replay).
sdk-connectors advertises a DLQ it never implemented (latent defect)Tracked as P15·E5 (EP-340): implement retry/DLQ/reconciliation on the proven sdk-webhook pattern and wire the /api/connectors/dlq/replay route the manifest already promises.
Workspace-only SDKs aren’t installable off the registry yetAdd a one-line publishConfig.registry and publish to Verdaccio, or vendor packages/sdk-…/src into InboundCRM. Low effort.
Scope creep from ProjexCRM features the SOP doesn’t needThe authoritative SOP validation is the gate: copy-list is 0, and ~68 ProjexCRM services are explicitly DROPPED (outbound prospecting, LinkedIn, MCP-fleet, agent-mesh). Build only what a P0 capability maps to.
Semantic mismatch — assignment/lead-scoring are geo/field-service tunedReuse the engine, replace inputs with B2B features (firmographics, account territory, intent). The P14 round-robin rotation makes sdk-assignment fair-share for host/lead routing.

Bottom line (revised 15 Jul 2026). Build InboundCRM as SDK-only: stand it up with the AI planner + projex init, install ProjexCloud SDKs for the platform and every SOP capability, and — instead of lifting ProjexCRM — build the outreach engine and the SOP’s unowned data objects as reusable SDKs (P14 + P15, already planned and tracked in ProjexLight). The authoritative SOP re-validation reduced the ProjexCRM copy-list to zero. This closes 100% of the SOP P0 gaps with reusable, coupling-free SDKs and the least app-specific code.
