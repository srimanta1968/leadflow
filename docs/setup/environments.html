Setup & Operations

LeadFlow — environment setup

How to stand up and run LeadFlow in development, QA and production.

Stack Express + TypeScript · React + Vite · PostgreSQL 18 (PostGIS) Node ≥ 20 Last verified 2 Aug 2026

Read this before trusting the production section

Only development is fully realised today. QA runs, but shares the development database by default. Production has no deployment pipeline, no container image for the app, no process manager and no CI — the production section below describes what the code supports and what you would have to supply yourself, and the Known gaps section lists exactly what is missing. Nothing here is a description of a running production system, because there isn't one yet.

The MCP server is not part of the application

It sits in the same docker-compose.yml as the database, which makes it look like a runtime dependency. It is not: it is the ProjexLight development agent that reviews code and syncs schema, and it mounts the whole repository at /workspace. Never deploy it alongside the app — it would put your source tree on a production host for no benefit.

2. Prerequisites

  • Node ≥ 20 — enforced by engines in the root package.json.
  • Docker + Docker Compose — for PostgreSQL. If you have your own PostgreSQL 18 with PostGIS and pgvector, you can point at that instead and skip Compose entirely.
  • Ports free: 3010, 5173, 5432. Both dev ports are checked before startup and both fail loudly rather than drifting — see §11.

4. Development

4.1 First run

# 1. Install everything (root, server, client)
npm run install:all

# 2. Environment files — three of them, one per workspace
cp .env.example .env
cp server/.env.example server/.env
cp client/.env.example client/.env

# 3. Start PostgreSQL
docker-compose up -d postgres

# 4. Start both dev servers
npm run dev

That gives you the API on localhost:3010 and the app on localhost:5173. Check the API came up healthily:

curl http://localhost:3010/health
# {"status":"ok","database":"up","timestamp":"..."}

/health is public by design and returns 503 with "database":"down" when PostgreSQL is unreachable, so it is a real readiness probe rather than a liveness stub.

4.2 What happens on boot

Three things run before the server accepts a request, in this order:

  1. Migrations (server/src/db/migrations/*.sql, filename order, one transaction each, recorded in _leadflow_migrations). Fatal if they fail — serving against an unknown schema is worse than not serving. Nobody creates tables by hand.
  2. Consent purposes registered upstream. Idempotent, not fatal.
  3. Role provisioning upstream. Idempotent, not fatal.

The last two run on every boot rather than once behind a flag, because a flag would be a local record of upstream state and would be wrong the moment someone edited the tenant directly. They are non-fatal on purpose: the app serves fine against an identity provider that is temporarily unreachable, and refusing to boot would turn their outage into ours.

4.3 Pointing at a different SDK gateway

npm run dev:sdk-cloud    # https://cloud.projexlight.com
npm run dev:sdk-local    # http://localhost:3500

A shell-provided value wins because dotenv never overwrites an existing process.env entry, so these need no file edits. Note the local gateway used during recent testing was http://localhost:4000 — check which port yours is on rather than trusting the script name.

5. QA and testing

The test suite runs against a real database — and migrates it

server/tests/setup.ts calls runMigrations() in beforeAll. With no override, that is your development database. The suite also writes and deletes rows. Before running the suite against anything you care about, point DB_NAME somewhere else. There is no separate QA database provisioned for you.

This is deliberate in one respect: migrating from the suite means the tests also prove the migration runner works, rather than assuming it. It is only the shared target that is a problem.

5.1 Running the suites

npm test              # server (Jest) then client (Vitest)
npm run test:server   # Jest only  — 229 tests / 14 suites
npm run test:client   # Vitest only
npm run typecheck     # tsc --noEmit, both workspaces
npm run lint          # eslint, both workspaces

5.2 An isolated QA database

The cheapest isolation is a second database in the same container:

docker-compose exec postgres createdb -U postgres leadflow_qa

# Windows PowerShell
$env:DB_NAME = "leadflow_qa"; npm run test:server

# bash
DB_NAME=leadflow_qa npm run test:server

Migrations self-provision it on the first run, so there is nothing else to seed.

5.3 The BDD / UI suite

Feature files live in tests/features/ (lead-capture-from-web-forms, ai-lead-routing, sla-management, basic-analytics-dashboard) and are driven by the ProjexLight runner from inside a container. Two consequences that are easy to trip over:

  • The Vite dev server binds all interfaces and explicitly allows host.docker.internal. Without that entry every scenario fails on its first navigate step with a plain 403 Blocked request — while a curl pre-flight from the same container still passes, because it is a 403 response rather than a refused connection.
  • Port 5173 is pinned with strictPort. It must not drift, because tests/config/test-config.json and the CORS allow-list in server/src/app.ts both hard-code it.

Scenario authoring trap. A Background: block placed above the first Scenario: does not execute. A suite written that way runs every scenario signed out, and looks like it passed. Use the @login:default tag instead.

6. Production

6.1 Build and run

npm run install:all
npm run build     # tsc + copy migrations → server/dist ; vite build → client/dist
npm start         # node dist/app.js

The build step copies the .sql migration files into dist/db/migrations. If that copy is ever skipped, the runner falls back to the source path so the app still boots rather than silently applying nothing — but a deployment that ships dist without src would then have no migrations at all. Ship both, or verify the copy.

The API does not serve the client

There is no express.static anywhere in server/src. npm start gives you the API alone. You must serve client/dist yourself — nginx, a CDN, or any static host — and set CORS_ORIGIN to wherever you serve it from, or every request from the app will be blocked by CORS.

6.3 The database

PostgreSQL 18 with PostGIS and pgvector — matching postgis/postgis:18-3.6, the image the Compose file pins. The pin is deliberate and must not be relaxed to a floating tag:

This previously read postgres:alpine, which was wrong twice over. It tracked "latest stable", so the major version moved on its own — and a new major pointed at an existing data volume does not migrate, it refuses to start with "database files are incompatible with server version". It was also the plain postgres image, without the PostGIS and pgvector extensions the platform database provides.

Upgrading a major version is a deliberate edit to the Compose file plus a dump/restore. Keep it in step with the generator's DB_IMAGE_PINS.

6.4 Process management

npm start runs one Node process in the foreground. It handles SIGTERM and SIGINT by draining in-flight requests and closing the connection pool before exiting, so it behaves correctly under systemd, Docker or Kubernetes. It does not restart itself, cluster, or write logs anywhere but stdout — supply that from outside.

Use GET /health as the readiness probe. It returns 503 while the database is unreachable, which is what you want a load balancer to act on.

8. ProjexCloud gateway & identity

LeadFlow owns no horizontal capability of its own — contact, consent, assignment, SLA, sequence and audit state all live behind the gateway. Two separate trust relationships, easy to conflate:

  • The gateway (PROJEXCLOUD_GATEWAY_URL) authenticates LeadFlow-the-application with an application credential.
  • Identity (PROJEXCLOUD_IDENTITY_URL) issues the session tokens LeadFlow verifies for end users.

8.1 Degrade-to-local

Both URL and key must be non-empty for the gateway to be used at all. While either is blank every caller takes its documented local fallback: SLA verdicts come from the wall clock instead of the business calendar, routing falls back to rule-match then round-robin, and alerts are raised but stay state=pending. That degradation is deliberate and loses nothing — but it is not the real thing.

Do not put a placeholder in the key. A non-empty fake flips isConfigured() to true and turns every SDK call into a 502 UPSTREAM_UNAVAILABLE instead of a clean fallback.

8.2 Credentials — three traps, all verified against a live gateway

What you sendResult
Authorization: Bearer <tenant JWT>200
Authorization: Bearer <pk_test_ key>403 recognised, not authorised
x-api-key: <key>401 header not recognised — there is no such header
  1. The SDK name is not a URL segment. {base}/api/source-records → 200; {base}/sdk-source-record/api/source-records → 404. The gateway serves every SDK's routes under one flat namespace and works out which SDK owns a path itself.
  2. A pk_ key is not a bearer credential. It is the client_secret for POST /api/auth/token. The client exchanges it automatically and caches the resulting token until 60s before expiry.
  3. The exchange is necessary but not sufficient. The token names a synthetic persona that starts with no role grants, and authority resolves from the persona at request time — so calls keep returning 403 until someone runs POST /api/personas/{persona_id}/roles. A valid key plus a clean exchange plus 403 is an ungranted persona, not a broken key.

The tenant-scoping trap, if you are pasting a JWT into the config: the token from POST /api/auth/login carries tenant_id: null and every tenant-scoped route refuses it. The token from POST /api/auth/signup-tenant carries the tenant. Two identities, and only one of them works.

8.3 Local vs cloud credentials

Each target has its own key — a cloud key will not authenticate against a local gateway or vice versa. Keep two files and switch between them; server/.gitignore ignores .env.* so neither is committed. docs/projexcloud-env.example.md is the committed template and holds no values.

9. Tenancy: root vs app

A ProjexCloud tenant row has a NOT NULL app_id, so one tenant row belongs to exactly one app. A customer running several apps is a root tenant with a child tenant per app.

Scoped toConcernsWhy
App (child)
PROJEXCLOUD_TENANT_ID		 leads, routing, SLA, consent, audit A lead captured in LeadFlow must not be visible to the customer's other product. That isolation is the point of the split — and an app-scoped audit chain stops one app's operator reading another's activity.
Customer (root)
PROJEXCLOUD_ROOT_TENANT_ID		 billing, org chart, cross-app reporting The customer is the payer and the employer once, however many apps. Scope billing to the app and one customer becomes several payers.

Leave PROJEXCLOUD_ROOT_TENANT_ID empty while a customer owns one app. Root and child are the same row, and the code falls back correctly. Set it the moment there are two.

Why this is configured before it is needed. Today the two collapse and nothing breaks. The moment a second app is sold, every tenant_id already written is ambiguous — customer or app? — and no later code can recover which was meant. Deciding now costs a config field; deciding later means migrating every tenant-scoped row against data whose meaning has to be guessed.

Current state: Modelled, not enforced. server/src/platform/tenancy/tenantHierarchy.ts encodes the split and is covered by tests, but the request handlers do not call tenantIdFor() yet. It is a recorded, testable decision — not yet an enforced boundary at the call sites.

10. Known gaps before production

GapSeverityDetail
JWT_SECRET has no guard Critical The app boots happily with the placeholder from .env.example. Anyone who has read this repository can then mint a valid session token. Nothing in the code refuses to start.
TLS certificates are not verified Critical DB_SSL=true sets rejectUnauthorized: false in DataService.ts. That encrypts the connection but accepts any certificate, so it does not authenticate the server — no protection against an interposed one.
No trust proxy, and rate limiting is capture-only High Two problems that compound. TRUST_PROXY exists in .env.example but is read nowhere, so behind a load balancer Express sees the proxy's IP for every request — and express-rate-limit keys on IP, so the limiter treats all traffic as one client. It is also applied to the public lead-capture route alone; every authenticated route is unthrottled. Both need code changes, not configuration.
Tests share the development database High The suite migrates and writes to whatever DB_NAME points at. See §5.2.
Local password authentication still exists High ProjexCloud's guide says not to keep a parallel users/roles/sessions store. LeadFlow still has users.password_hash. Mitigated: setting PROJEXCLOUD_IDENTITY_URL now disables local password auth with 501, so the two stores cannot both be answering. The table is dropped only once personas are provisioned for existing users.
Identity keys on users.id, not persona_id Medium Migration 007 adds the persona columns alongside the user ones, nullable. Dual-write, backfill, read-switch and drop are still to come — steps that need a reachable tenant.
No deployment pipeline Medium No CI (.github/workflows does not exist), no application container image, no process manager config, no secret management. All must be supplied.
No static hosting for the client Medium See §6.1 — the API does not serve client/dist.
Four services still send /v1 paths Low SlaMonitorService, LeadCaptureService, RoutingService, SlaAlertService. /v1/source-records 404s against the real gateway; the catalog path is /api. Currently invisible because each wraps the call in degrade-to-local.

11. Troubleshooting

Port already in use

npm run dev refuses to start if either port is taken — reported once, clearly, by the predev hook, rather than a raw EADDRINUSE stack trace repeating every few seconds under ts-node-dev --respawn. Almost always a dev server from an earlier session.

# Windows
netstat -ano | findstr :3010
taskkill /PID <pid> /F

# macOS / Linux
lsof -ti tcp:3010 | xargs kill

# Or move both together — they must agree
PORT=3011 VITE_API_TARGET=http://localhost:3011 npm run dev

PostgreSQL 5432 clash

Usually a local PostgreSQL service. Set DB_PORT=5433 in the root .env (replace the line, do not append), then docker-compose down && docker-compose up -d.

"database files are incompatible with server version"

The image's major version changed under an existing volume. PostgreSQL does not auto-migrate majors. Either restore the previous pinned image, or dump on the old version and restore on the new. docker-compose down -v would fix it by deleting all data — only acceptable on a throwaway dev volume.

Every ProjexCloud call returns 403

Work down §8.2 in order: is the credential a pk_ key (needs exchange, which the client now does), is PROJEXCLOUD_APP_ID set (it is the client_id for that exchange), and has the persona been granted a role. The third is the one that is almost always missing.

Every ProjexCloud call returns 404

Check the path does not include the SDK name as a segment, and that it starts /api rather than /v1.

The gateway seems configured but nothing reaches it

Check both PROJEXCLOUD_GATEWAY_URL and PROJEXCLOUD_API_KEY are non-empty. Either being blank silently routes everything to the local fallback, which looks like working software.

Every BDD scenario fails on its first navigate step

host.docker.internal is missing from allowedHosts in client/vite.config.ts, or the dev server drifted off port 5173.
