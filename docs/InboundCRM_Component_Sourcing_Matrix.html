The core insight. The SOP capabilities ProjexCRM was missing (identity, RBAC, SLA/routing, backup coverage, consent, audit, SMS, payment, workflow) map almost 1:1 onto mature, v1.0.0 ProjexCloud SDKs. The capabilities ProjexCRM is strong at (email send, sequence cadence, reply-sync, booking) map onto early / semantically-mismatched SDKs (sdk-campaign 0.1.0, sdk-engagement = field-service, no calendar SDK). So the two sources are complementary, not competing — SDKs supply the platform & the gaps; ProjexCRM supplies the proven outreach engine.

1 · The SDK-vs-Copy decision rule

Every capability was scored on four axes. The winner per row in §2 follows this rule:

  • Prefer an SDK when it is v1.0.0 + publishConfig and semantically fits — because it is (a) already the missing SOP capability, (b) maintained centrally, (c) audit/policy/identity-wired by design. → identity, rebac, policy, tenant, consent, notification, workflow, webhook, payment, billing, approval.
  • Prefer an SDK with adaptation when the engine is real but tuned for another vertical (field-service/geo) — reuse the engine, re-model the inputs for B2B. → assignment, dispatch, lead-scoring, identity-resolver, ingest, crm. These are workspace-only (no publishConfig yet) → add publishConfig or vendor.
  • Lift from ProjexCRM when ProjexCRM has a battle-tested implementation and the SDK equivalent is early (0.1.0), a stub, or semantically wrong. → email send transport, sequence cadence engine, IMAP reply-sync, bounce/suppression deliverability, calendar/booking, pipeline board.
  • Build new only where neither source fits: the leadership operational dashboard, the NEXT-action save-gate, offer/feature-status matrix, and closed-won→onboarding orchestration (composed from sdk-workflow).
Registry fact that makes this possible. ProjexCloud publishes @projexlight/* packages to a private Verdaccio registry (.npmrc → http://localhost:4873/, prod npm.projexcloud.com). A separate project can install the ~14 publishConfig SDKs as versioned deps today; the rest need a one-line publishConfig add or vendoring.

6 · The only coupling threads to cut

Lifting is safe because the entanglement is localized to two threads — neither is structural:

  • Billing gate: inline creditService.canAfford/deductCredits in send-queue-processor and sequence-step-executor → swap for sdk-billing/sdk-meter or a no-op.
  • Prospecting refs: prospects/prospect_id, emailPatternIntelligence, base-agent, domain-vocabulary, product-alignment → delete the branches (all optional/nullable).

Plus the DB layer: ship no db.config.json and dataService collapses to a single pool automatically — the multi-tenant sharding code becomes inert.

Composition follows the ProjexCloud api-gateway pattern: one backend process that app.register()s each SDK’s routes and appends each SDK’s migrationsDir to a single boot-time runMigrations([...]); the frontend is a Next.js app (like apps/tenant-workspace) using @projexlight/design-system over HTTP. See Report 2 for the full recipe.

Method. Findings from parallel source inspection of ProjexCloud (packages/sdk-*, docs/v3.1, blueprints, api-gateway) and ProjexCRM (server/src).
